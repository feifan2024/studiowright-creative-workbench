# Gemini CLI 调用稳定性审计 · 2026-11-18

## 结论与检查范围

检查当前 Ubuntu 部署代码、实际 CLI 帮助和版本、九账号配置、原调用回执、近 24 小时/7 天请求记录。未发送新模型请求，未改变派发、授权或运行代码。

九账号共享同一个 Antigravity agy 1.5.10 二进制，工作台固定模型为 gemini-3.8-flash-medium。当前实现是受限的文字和多模态接入，不是把 CLI 的全部代理能力开放给 API。模型 ID 是本机配置值，此次没有核实供应商的公开型号命名。

数据为检查过程中的只读快照，窗口随时间滚动；unknown 是结果未确认，不等于供应商生成失败。

## 已确认的稳定性问题

### 1. 文字固定 150 秒截止，长请求被本机主动截断

official_runtime.py 通过 --print-timeout 150s 启动 CLI，外层另有 180 秒上限。
近 24 小时 23 个文字超时的原始 result.json 全部带 cli_print_timeout=true；抽查 CLI 最终事件为 ERROR / finished_reason=print_timeout，结束耗时约 156～157 秒。

这证明超时分类由本机时限触发；不证明延长后一定成功，也不能排除远端本身很慢。需要可配置的整体期限、无进展期限和阶段记录，不能仅把“有回复但还没完成”当断线。

所有 152 条业务文字均携带 no_retry=1，当前调用方明确关闭了自动重试；23 条文字超时均只执行一次。这是请求策略，不是后台忽略了重试开关。不得擅自打开重试。

### 2. 识图同样有硬期限，且线上与仓库源码不同

线上 material_vision.py 的 session/prompt 当前截止为 200 秒；仓库副本仍为 145 秒。
近 24 小时识图超时耗时同时有约 149～152 秒和约 205～210 秒，表明既有旧阈值下的记录，也有延长后的记录。不能把全部异常说成当前 145 秒造成。

两个副本 SHA-256：
- 线上：cb0fb0113c4edd24d49da115592d0ece250bda52e5e5bf711fee784640749715
- 仓库：4b4b476b1402818e4b97769b07bd21820aab6017fda8965a687b2e8850d7018d

应先核对差异并同步版本，避免下次打包把线上修复覆盖回去。此次未覆盖任一版本。

### 3. 验活与业务共用并发池，造成可避免的排队

共享最大并发为 2。检查开始时，2 条执行和5条排队全部是验活，后续观察仍为2条验活执行、2条排队。
近24小时有98条验活，经常按7个账号成批提交。不能由数据库直接判断是用户点击还是外部程序发起。

当前 recent_readiness_probe 只保护近30秒或仍在处理的重复验活。健康账号无需为了继续正常调用不断重新验活；验活适合手动或有具体错误时做定向检查，并应避让业务任务。

### 4. 遇到工具步骤直接终止，属于接入策略限制

文字 event_line 看到 step_type=tool 就置 unexpected_tool_stopped；ACP 遇到工具请求或工具更新也直接异常退出。
近7天有27条文字工具中止和1条识图工具中止；近24小时文字没有这类记录，识图仍有1条。不可把历史问题夸大成今天文字的主要原因。

应保持工具权限边界，同时支持“拒绝工具请求后继续给普通文字回复”的协议处理；不能简单开放所有工具来追求成功率。

### 5. 识图未完整执行 retry_policy=never

文字 run_text 在运行后立即检查 job.no_retry。
run_image 没有对应检查，在部分已确认坏回复/空回复条件下仍可能调用 reserve_retry 并发出第二次识图。现有24小时超时样本没有发生这种重试；这是代码检查发现的具体一致性缺口，不能宣称已经导致了现有超时。

### 6. 授权恢复仍有并发风险，需要进一步验证

九个账号的令牌和备份当前都存在，工具拒绝设置完整。
account()/inventory() 在读状态时也可能备份、恢复令牌；与 CLI 自身令牌轮换没有共同的账号级文件锁。恢复旧备份可能与刷新中的新文件竞争，这是待验证风险，不能把它写成已经抓到的删除原因。应把状态检查与凭据写入协调起来，而不是在任意读状态时抢写令牌。

## 当前供应商与主机状态

- Google 授权和 Gemini 两个入口通过本机 127.0.0.1:7897 代理可连接；仅代表检查当时网络正常。
- 两账号的业务调用确实返回 verification_required，当前不是单纯额度读取失败；不能靠修改就绪数字解除供应商验证。
- 近24小时有6次尝试记 provider_unavailable；历史网络/上游异常仍存在。
- 检查时主机约24GB内存，available约11GB，swap未使用，负载约1；没有资源耗尽证据。
- 近24小时还有3次尝试记 workbench_restarted。服务更新期间的中断也应单独计数，不混作模型能力缺失。

## 修复顺序

1. 统一线上与源码版本，明确文字/图片的超时配置和无进展判断；保留中间回复与原因，不擅自重发。
2. 减少全账号验活，让检查避让实际业务；将排队、模型处理和授权阶段分开显示。
3. 修正识图 no_retry 一致性；完善工具拒绝后的继续回复流程。
4. 协调令牌轮换与恢复，补充进程级凭据变更证据。
5. 再按独立文字、多轮、单图、多图、视频抽帧做少量定向实测，既看内容正确性，也看时延和是否完整结束。
